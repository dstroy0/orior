# The orior app: completed roadmap

What the window does that [the roadmap](ROADMAP.md) asked of it, by area. Each time given is measured with real keys on a file of 2,677 lines, from the key's press to the screen showing its answer.

## Responsiveness

1. **Go to File puts the exact name first.** A file whose name is what was typed comes above a longer name that holds it, and a name that starts with it comes next.
2. **No browser autofill.** Every field of the window refuses the web view's list of words typed before, and a search's results stand clear.
3. **Completion as you type.** The list opens on its own as a name is begun, as well as on Ctrl+Space. One question to the language server answers every letter typed while it is out, and the list stands about 0.85 s after the first letter.
4. **The minimap moves with the text.** A scroll or a jump redraws the minimap in the same frame as the code: a page down settles in about 110 ms, minimap and all.
5. **A language server ready before it is asked.** The server for each tab a tree reopens starts as the tree opens, and a file handed to its server is read through at once. A language with no tab open starts no server, and a tree opened in place of another stops the servers the first started. Go to Definition three seconds after a file opens answers in about 135 ms, as quickly as the next one.
6. **A tab back at its saved text shows no change.** Typing a letter and taking it out again leaves the tab marked as saved.
7. **A large file as quick as a small one.** A file of 50 MB and 870,025 lines opens in about 120 ms, goes to its end in about 170 ms, takes a letter there in about 60 ms and pages in about 120 ms: each the time the file of 2,677 lines takes, and each settled as soon. The rest of the file is read in behind the view, by the page's clock 2.6 s from its top or 5.3 s from its end, and a row far down it is drawn as sharply as the first.
8. **Smooth motion counted.** Counted frame by frame on a display that draws 120 frames a second: the lattice draws at about 114 a second and misses none of 60, and a burning fuse holds all 120. A fast scroll through a file of 2,677 lines or of 870,025 holds 60 a second, missing at most 4 frames in 4 s, and reaches 77 to 88 of the display's 120.
9. **Start measured.** Launched cold from the release build, the window is drawn in about 0.96 s and its keys are bound in about 1.04 s: the middle of five launches, each read from the page's own clock against the moment of the launch. The page itself starts about 0.65 s in.
10. **Go to File matched in Rust.** Go to File sends what is typed to files.rs, which holds the tree's files with their names in lower case, reads them again behind the search once they are four seconds old, and gives back the best 200 with the letters that matched, scored as the palette scores them. No list of the tree's files crosses to the page, where reading one took 119 ms on the window's own thread and was done again every 20 seconds. In the release build a keystroke's answer comes back in 1.9 to 3.6 ms over the 2,836 files of this repository, where matching them in the page took 0.7 to 4.8 ms, and the work grows with the tree in Rust and not in the page.
11. **Start under a second.** Launched cold from the release build, the window has its page drawn in about 0.76 s and its keys bound in about 0.79 s, the middle of five launches and the slowest 0.85 s, each read from the page's own clock against the moment of the launch. The lattices start once the keys are bound: their first drawing sets up WebGL, and the menu bar's commands, read before the keys bind, no longer wait behind it.
12. **The highlighter in Rust.** The colors of the editor's lines come from orior's own Rust: each grammar is handed to it once and kept, with a regular-expression engine of orior's own that reads the syntax the grammars write, and the lines an edit reaches, a screen's worth below it, are asked for as the edit is made, the answer coming before the frame that draws it where it can. Until it comes, a line keeps the tokens it had, moved with its line. A jump into a large file colors there off the page's thread. Fifty thousand lines take about 0.12 s against 0.19 s in the page, and every bundled grammar colors as the page did, line for line, over 23,620 lines of the tree and of lines made from each grammar's words. A grammar holding what the engine does not read, lookbehind or a named group, is colored in the page as before, and so is the token at a place that editing asks for at once.
13. **Memory held down.** The memory reading counts each process with the one the app started it from, names a language server by its program and the web view as the web view, and shows on the bar beside the total the name of what holds the most. View, Memory Budget sets the megabytes the app is held to, 2048 where none is set, kept with the settings; a press on the reading lists each part, sets the budget, and stops the servers no open tab needs. While the reading is over the budget it is marked, and the app stops the servers no open tab needs, then the one that holds the most and does not serve the tab shown; each stopped server's tabs lose their diagnostics and are handed to a server again as each shows, and the bar says what was stopped. anchor_sift open with its Python server holds about 300 MB in RAM.
14. **Smooth and gliding scrolls.** A wheel's step over the text or the gutter, and Page Up and Page Down, glide over 130 ms, easing out, a step during a glide taking up from where it is heading; a cursor kept in sight during a glide moves the glide's end and not the view. A touchpad's movement follows the fingers, and once they lift and no event comes for 50 ms, the system giving no run of its own, it runs on from its last speed and slows to rest; any wheel stops it. View, Smooth Scrolling and View, Flick Scrolling set each on or off, kept with the settings, both on where none is kept.
15. **A restart that loses nothing.** orior started again opens each tree with every tab it had, every change not yet saved in its text, each tab's cursor, and the split with its file and its way, which the tree's session now keeps as it changes. The terminal keeps its place: whether its panel is open, the folder its shell stands in, which Git's bash is set to say before each prompt as OSC 7 and any shell that says it is heard, and its last 300 lines, kept a moment after the shell writes and as the window closes. Started again, the panel shows those lines and opens as it was, its shell in that folder.

## Code intelligence

1. **Symbols of the whole tree.** Go to Symbol in Tree, Ctrl+T or `#` in Go to File, and Search Everywhere find a declaration in any file of the tree, from an index of what each file declares, read by the line as the outline reads the open file. A file is read again once it changes. The whole of this repository is read in about 1.1 s, behind the window, and a search answers in about 70 ms.
2. **Refactorings of orior's own.** Extract Variable, Ctrl+Alt+V, and Extract Constant, Ctrl+Alt+C, put the expression selected into a variable above its statement or a constant at the head of the file, and leave the new name selected in both places for the name typed next. Inline Variable, Ctrl+Alt+N, puts a variable's value where it is used and takes its declaration out, and refuses where the variable is given another value. Each is one change undo takes back, in Python, JavaScript, Rust, the C family, Ruby, R, MATLAB, Octave and PowerShell, from the Edit menu's Refactor group and the editor's own menu.
3. **Extract Function.** Ctrl+Alt+M puts the lines selected, or an expression on one line, into a function of its own after the definition that holds them, in Python and JavaScript. It takes as parameters what the selection reads that its function set before it, and gives back what the selection sets that its function reads after it, several of them in Python as a tuple. A selection that returns, or that leaves a loop it does not hold, stays where it is. Each Python result tried runs and prints what the code it came from prints.
4. **Extract Function in Rust and the C family.** The same key in Rust, C, C++ and CUDA types each parameter and what the function gives back from the language server's hover, and an expression's type from the server's hover on a declaration of it shown to the server for that question alone. In Rust a value read again after the selection goes by reference, or by a mutable reference where it is declared `mut` and the selection reaches into it, several values come back as a tuple, and a selection that reads `self` becomes a method of its impl. In the C family the function goes above the one that holds the selection, as C needs, and a field out of reach or more than one value to give back is said and not written. Each Rust and C result tried builds and prints what the code it came from prints.
5. **More refactorings of orior's own.** Change Signature, Ctrl+F6, changes a function's parameters in its declaration and at every call of it in the tree, in JavaScript, Python, Rust and the C family. A sheet lists its parameters as written, each to write anew, move up or down, or take out, and a parameter added is given the value each call passes for it. Each call's arguments move as their parameters moved, a gap takes a parameter's default, and Python's keyword arguments take a parameter's new name. Move, from the Refactor menu, puts the declaration on the cursor's line, with the decorators and comments above it, at the end of another file of the tree, made where it is not there. In JavaScript it is exported there and imported where the file it left still names it, and in Python the file it left imports it from the new file's module. Each is one step that undo takes back in every file it changed, from any of them, where no language server offers it; a file Move made stays after an undo, empty.
6. **Problems of the whole tree.** Problems lists what is wrong in every file of the tree, and not only in the files open. Once Problems shows, every file the editor does not have open is handed to its language's server, six at a time, and let go once the server has said what is wrong in it, by its answer where it answers a question about a file and by its own word where it does not; rust-analyzer checks each crate whole with cargo check. The pane says how far the check has gone, and a file's row opens and closes its problems, those of a file open in the editor open from the start. A file that changes on the disk is checked again with the files whose includes or imports name it, a file the editor holds is read again against a header that changed under it, a file taken out loses its rows, and a file closed in the editor keeps its problems as the disk holds it. While the check goes on, the memory budget stops no server. The whole of this repository, 1451 files of C, CUDA and Python and two crates, is checked in about four minutes, and the pane draws its 768 files in about 17 ms.
7. **Inspections.** Checks of orior's own over the tree's Python and JavaScript, in Rust, run as files change on the disk and in the editor, each listed in Problems beside the servers' diagnostics and drawn under the text, with Quick Fix, Ctrl+., offering a finding's fix in any tab, one no server serves too. An import that leads back round to the file that makes it is named with the files it passes through. A name a function sets and never reads is found, and its fix takes it out, keeping its value where the value calls something. Code no path reaches after a return, a raise, a throw, a break or a continue is found, and its fix takes it out. A docstring out of PEP 257's form is found in its quotes, its lines, its period, its blank line and its closing quotes, most with a fix. An attribute a method reads of `self` is found where neither its class, a class it comes from, nor a class that comes from it sets it: a method a mixin class supplies is taken as found, and pyright's report that the mixin has no such method is not passed on. The whole of this repository, 783 files, is read in about 0.6 s.
8. **Call hierarchy.** Go, Call Hierarchy, Ctrl+Alt+H, shows the functions that call the one at the cursor and those it calls in the Call Hierarchy pane, each a tree that opens a level at a time by its arrow or the list's keys, a press on a function going to its call. A language server that answers for calls, as clangd, pyright and rust-analyzer do, gives them; where none does, orior's own index of the tree's Python and JavaScript functions finds them, a call of a name reaching the functions of that name in its file, or in the tree where its file declares none.
9. **Types written in the text.** The types a language server infers for names and the names of the parameters an argument meets, as rust-analyzer and clangd give them, are drawn in the line in a smaller face and are not part of it: a type after the name, a parameter's name before its argument. The caret, a press, a selection and the marks under the text each allow for them, and a hint stays with its line as lines are added or taken out around it, asked for again for the lines shown once typing and scrolling rest. View, Inferred Types and View, Parameter Names set each kind on or off.
10. **Diagnostics in their own form.** A diagnostic whose server writes it in Markdown shows in the hover as written: its code as code, its links as links and its lists as lists, under a heading that names its severity, who said it and its code, the code a link to the page that tells of it where the server names one. orior's own findings are written so, a name as code, an import's way back round as a numbered list of its files, and a PEP 257 finding linked to PEP 257. Problems sets a finding's code as code in its row. A press on a link opens the page in the browser, an https page only, and the window stays where it was.
11. **Highlighting from a parse.** A Python or JavaScript file is colored from orior's own parse of it, in Rust, read whole as it changes and not from patterns over a line at a time: every name by what it is, a function's, a class's, a parameter's, an attribute's or a module's, each a color of the theme's that Preferences sets. A file a language server serves takes the server's semantic tokens over its patterns, as rust-analyzer gives them. The regions that fold come from the same parse, or from the server's folding ranges, and Expand Selection steps through the parse's spans, a string, the inside of its brackets, the brackets, the statement and the block, or through the server's selection ranges. A line typed keeps its colors until typing rests and the parse reads it again. The largest file of this repository, 3425 lines, is parsed in 7.5 ms.
12. **Structural search and replace.** Edit, Search Structurally finds code by its shape in the file open or in every file of the tree in its language, read as the editor holds it, in Rust: a pattern is code with placeholders, `$x$` for an expression, `$x:name$` for one name and `$x:stmt$` for statements, read as tokens past spaces, line breaks and comments, a placeholder named twice matching the same code both times. Each match is listed under the sheet's fields, a press going to it. Replace All writes every match again from a template that uses what the placeholders took, every file's changes one step that undo takes back. The last pattern and template are kept, by language.
13. **Code written for the reader.** Edit, Write Docstring draws up a docstring for the function the cursor is in from its parameters and their annotations, what it returns or yields and what it raises, in Rust, and leaves the cursor on its summary line: for Python in the form Edit, Docstring Form chooses, Google's, NumPy's, reStructuredText's fields or a summary line alone, and for JavaScript as JSDoc. Edit, Sort Methods by Name sorts the methods of the class the cursor is in, Python's or JavaScript's, each with the comments and decorators over it, the class's other members and its blank lines staying where they stand. Each is one change undo takes back. File, Create, Project from Template begins a project in a folder chosen as a copy of one of the reader's templates, the folders in `templates/` in orior's own folder, `{{name}}` written as the project's name in every file's name and text, and opens it; File, Keep Tree as Template keeps the tree open as one.
14. **Regions in Structure.** The regions a file's comments mark, as `# region Name` and `# endregion`, `//#region`, `#pragma region` and `<!-- #region -->` write them, show in the Outline as nodes that hold what stands in them, a region inside a class under the class, each opened and closed by its arrow or the list's keys; a line of code that names a region is none. The Outline's menu pins it to the file shown, its head naming the file, and it stays on that file while another is open, a press on a symbol going to it, until it is unpinned or the file closes.

## Languages and formatting

1. **The formatter's own settings, and its width drawn.** Format Document and Format on Save run Black for Python, rustfmt for Rust, clang-format for the C family and Prettier for the web's languages, each reading the project's own settings. rustfmt formats by the edition the crate's Cargo.toml names. A line down the editor marks the width the formatter keeps lines to: Black's `line-length` in a pyproject.toml, rustfmt's `max_width`, clang-format's `ColumnLimit` and Prettier's `printWidth`, or the formatter's own where the project sets none, 88 for Black.
2. **Typing as Black writes.** Enter after a bracket the line leaves open, outside its strings and comments, puts the new line one step in, as Black, rustfmt and Prettier lay out a call that runs past one line, and where the cursor stands before that bracket's close, the close goes down to a line of its own at the first line's depth. A closing bracket typed at the start of a line steps back to the depth of the line that opened it.
3. **Type checkers and linters in the editor.** View, Checkers names the checkers to run, ruff, flake8, mypy, Pylint, ESLint and ShellCheck among the toolchains, each found as any toolchain is and needing nothing set up past its name. Each checks a file as it opens; one that reads a file on its input, as ruff, flake8, ESLint and ShellCheck do, checks it again as it is typed, and every one checks it as it changes on the disk, mypy and the rest over the tree whole with the tree's check. Their findings are drawn under the text and listed in Problems beside the language server's and orior's own, each named by its checker, and a fix a checker gives, as ruff does, is offered by Quick Fix. A name no checker answers to is said.

## Explorer and files

1. **Type to search in the explorer.** Letters typed while a row of the explorer, or of the jobs, holds the keys find the rows in sight whose names match them, as Go to File matches a name. The first match from that row on takes the keys, each match's letters are marked, Up and Down step from match to match, and Backspace takes the last letter back. What was typed shows over the list's top right, in the fail color where nothing matches. Escape, a click in the list, a key that opens or closes a row, or the keys leaving the list ends the search.
2. **Files between windows and the system.** Cut and Copy in the explorer's menu, or Ctrl+X and Ctrl+C on a row, put the file or folder on the system clipboard as the system's file manager puts its own, and Paste, or Ctrl+V, puts the files on the clipboard into the row's folder. Another window of orior and the file manager paste what orior put there, and orior pastes what they put there. Files cut are moved when pasted, the file manager's own cut among them, and the clipboard is cleared after. A name the folder holds already is numbered, and nothing is written over. The tab of a file moved follows it. On Windows the file manager reads orior's cut as a cut; elsewhere a cut is a move only in the window it was made in.
3. **Every file but some.** Preferences, under Files, holds a list of patterns for each of the explorer, the search and the watching of files, one to a line, each read as a `.gitignore` line is: `*` any letters of a name, `**` any folders, a trailing `/` folders only, and a name alone matching wherever it stands. A pattern starting with `!` keeps the files it names and hides every other: `!src/**` alone keeps the explorer, or the search, to the files under src. The explorer and its filter leave out what their list hides. Find in Files hands its list to git as pathspecs, and Go to File leaves out the same files. The window watches the tree: on Windows the system tells of each change as it is made, and elsewhere the tree's files are read every two seconds. A file or folder made, moved or taken out outside the window shows in the explorer within a second. A tab with no changes of its own takes its file's new text as one change undo takes back, and a tab with changes keeps them while the status bar says the file changed. Git's marks are read again when its index, HEAD or a file it tracks changes. The watching leaves out what its own list hides.
4. **Search in a set of files.** Preferences, under Files, keeps sets of files by name: a name ending in `:` on a line of its own, and under it the patterns that name the set's files, one starting with `!` taking files out. While any set is named, the Search pane offers the whole tree or each set under its field, and the one chosen is kept for the next start. A search in a set hands git the set's patterns as pathspecs, with the search's own patterns as well.
5. **Breadcrumbs that go somewhere.** A press on a folder's crumb, or the file's, opens over the status bar the list of the files and folders in the folder that holds it, with it chosen. A file in the list opens at a press, and a folder opens its own list beside it, as many levels down as the reader goes, each folder read only as it opens. A press on a symbol's crumb lists the symbols beside it, and the one chosen is gone to.
6. **orior's own files in one place.** Its settings, its themes, its plugins, its stylesheet, the toolchains added, its kept state, the text of each tab with changes not saved, Local History and the repositories it clones are in orior's own folder, laid out as the README's "orior's own folder" says. The window writes each entry there a moment after it changes and reads the folder back as it starts, which takes in an edit made while it was closed. `settings.json` and `state.json` hold each entry under its own key as JSON, each theme is a file in `themes/`, and each tab's changes not saved a file in `backups/`.

## Editing

1. **Macros.** Edit, Macros, Record Macro records what the editor's keys do and the text typed, each cut, copy and paste among them, until it is chosen again, and the status bar says how many steps it took. Play Back Last Macro plays it, as many times as its first word on the command line says, and Keep Last Macro keeps it under a name. Each kept macro is listed under them, to play once or many times, to forget, or to bind keys to by pressing them, and its keys play it in the editor. The palette lists the kept macros, and `settings.json` keeps them. A macro playing starts no other.
2. **A history of undo that branches.** The text's undo history is a tree of every state it has been in since it opened. Undo goes to the state before and redo to the state undo last left, as they did; an edit made after an undo starts a branch, and the states undone stay in the tree beside it. Undo History, beside Outline and under Edit, lists the states from the first, each by when it was made and the line it changed, a branch a level in under the state it was made from, the state the text is in marked. A press on a row takes the text to that state, undoing back to the state it shares with the one it is in and redoing on to it.
3. **Jump to any place on the screen.** Go, Jump to a Place, on Ctrl+;, takes a letter or two and looks for them in the lines in sight, case aside, and marks each place they stand with a letter of its own, the nearest the cursor first. Typing a mark's letter puts the cursor there. After one letter typed, no mark takes a letter that follows a place found, which leaves that letter free to look for two. Escape, a press, a scroll, or any other key ends it.
4. **Vim's keys.** Preferences sets Vim's keys on or off, kept in `settings.json`, and the status bar shows the mode first, NORMAL, INSERT, VISUAL or VISUAL LINE, with the keys of a command typed so far. Normal mode takes a count and a register before a command; the motions h j k l, w b e and W B E, 0 ^ $, gg and G, f F t T and ; , to a letter, %, { }, n N, and Ctrl+D and Ctrl+U; the operators d c y > < on a motion, on a text object (iw aw iW aW, and i or a before a quote or a bracket), or doubled on whole lines; x X D C Y s S J ~ r, p P, u and Ctrl+R, i a I A o O, v V, / ? * #, and `.`, which does the last change again with the text typed after it in insert mode. Visual and visual line mode move an end by the motions, take a text object, swap the ends with o, and act on what is chosen. Outside insert mode the caret is a block over its letter, and every key held with Ctrl that Vim gives nothing to stays the editor's.
5. **What is not drawn.** View, Show Whitespace lays a faint dot over each space, an arrow over each tab and a mark after each line's end, none of them moving a letter. View, Hide Comments, on Ctrl+Alt+/, stops drawing comments and takes the lines that hold a comment alone out of sight as a fold does, by the language's own comment marks, and the same keys show them again. Both are kept in `settings.json`.
6. **Folds that keep the close.** A folded block takes in the line after it where that line holds closing brackets alone, with any commas and semicolons after them, at the depth of the line that opens the block, and draws them after the fold's mark on its first line: `function one() {⋯}`, `const list = [⋯];`. A line that closes the block and opens another, as `} else {`, stays a line of its own, as does the close of an outer block; and the cursor going to a fold's closing line opens the fold.
7. **Print.** File, Print sends the file open, or the lines the selection takes, to the system's print dialog: each line with its number, a long line going on under itself, the tokens in the light scheme's colors on white paper whatever scheme the window is in, and the file's path as the page's title.
8. **Colors from the text.** A file with color codes in it, as a log or a run's output keeps, opens in the colors and weight its codes set, the codes taken out of the text and a color carried on from one line to the next, read as the terminal reads them: the sixteen colors, the 256, any as red, green and blue, bold, dim, italic, underlined and struck through. The tab is read-only while it shows its colors, and its lock gives back the text with its codes as written, to edit.
9. **Columns past the end of a line.** With View, Cursor Past Line Ends on, kept in `settings.json`, Right goes on past a line's end, a press past it puts the cursor where it was pressed, up and down keep a cursor's column over short lines, and Backspace there steps back a column; the status bar counts the columns past the end. A press with Alt held that then moves selects a column, as Alt with Shift does, and the cursors it puts on short lines stand in the same column past their ends whatever the setting. Text typed or pasted at a cursor past its line's end fills the line out with spaces to it first.
10. **Indentation by file.** A file opens with the indentation read from its own lines, then whatever `.editorconfig` files over it set, the nearer over the farther up to one that says `root = true`, each section's pattern read as EditorConfig reads it, and over both a mode line among its first or last five lines, as Vim (`vim: set sw=2 et:`) or Emacs (`-*- indent-tabs-mode: nil; tab-width: 4 -*-`) writes one. The status bar shows what the file indents with.

## Version control

1. **Branches.** A Git menu holds Commit, Push, Pull, Branches and New Branch. Branches, or a press on the branch in the top bar, lists every local branch and then every remote one, newest commit first, the one open checked. Each opens a list of its own: Switch, a remote branch made a local one that follows it; Merge into the branch open; Rebase the branch open onto it; and for a local branch Rename and Delete, a branch with commits no other holds deleted only after a yes. New Branch makes a branch from the one open and goes on it. What git says shows on the status bar, its own words where it refuses, and the tree's changes are read again after.
2. **Conflicts.** A file a merge left in conflict opens from Git, Resolve Conflicts, or from its row in the Commit window, in a window of three panes over the editor: the branch open's text on the left, the result in the middle, and the text the merge brought in on the right, each stretch the three share level across them and each side named as git named it. Each conflict takes its lines in the middle from Yours, from Theirs, from Both one after the other, or as written by hand in Edit, its open result striped until then. Once none is left open, Mark Resolved writes the result, stages the file as resolved, and gives an open tab of it the result. F7 and Shift+F7 step from conflict to conflict.
3. **Part of a file in a commit.** A changed or new file's arrow in the Commit window opens its changes under it, each change with a box of its own and each line taken out or added with one, the file's own box half filled while it is taken in part. The commit takes of the file only the lines whose boxes are checked, made from an index of its own so that nothing else staged goes with it, and the lines left out stay changes of the file for a later commit. A file that changed since its changes were opened is refused until they are opened again.
4. **Compare.** A revision in the Timeline opens beside the file as it stands, or beside another revision from its own list, the older on the left. Select for Compare on one file in the explorer and Compare with it on another puts the two side by side, and Compare with Clipboard in the Edit menu puts the clipboard beside the open file. A box over the changes sets changes to white space aside, which then show as the same, and the choice is kept.
5. **The commit graph.** The Git pane draws every branch's commits as a graph, the newest first, each in its column with a line to its parents, a merge's dot hollow, and the branches and tags at it, its subject, its author and its date. A press on a commit, or Right, opens the files it changed under it, and a press on one of those sets the file as the commit left it beside the file as the commit before it did. The field over the graph searches the whole history by subject, author, id or branch. The graph is laid out in the app's Rust side, two thousand commits at most.
6. **Line history.** Git, Line History puts a column in the gutter beside the line numbers with the date and author of the commit that last changed each line, on the first line of each run of lines one commit left, the commit's id and subject under the pointer. It reads the text as the editor holds it: a line typed in and not yet committed has no mark, the lines after it keep theirs, and the column is read again as the text or the file's last commit changes. A press on a line's mark sets the file as that commit left it beside the file as the commit before it did.
7. **Stash and cherry-pick.** Git, Stash Changes puts every change aside, new files with them, under a message, and Git, Stashes lists each stash, the newest first, to apply and keep, pop, or drop. Git, Cherry-Pick lists the commits of other branches the branch open does not hold, merges aside, and applies the one chosen as a commit of its own; a commit already applied under another id is left out, known by its author, the time its author made it and its message. A commit's menu in the Git pane cherry-picks it too. Where a change does not fit, its files stay in conflict for Resolve Conflicts, and a commit after finishes it.
8. **More than one repository in a tree.** A tree's repositories are found under it, the one it is in and each folder up to four deep that holds one of its own. The Commit window lists each one's changed files under a row that names it, its branch and how many files differ; a commit goes to each repository that holds a file taken, and Commit and Push pushes each. The branch on the status bar is the repository open's, the one that holds the file shown, named with it, and the Git menu's branches, stashes, cherry-pick, pull and push act on that repository. The Git pane chooses whose graph it shows. A file's last commit, Timeline, Line History and roll back are read from the repository that holds the file.
9. **Compare by structure.** The changes view's Compare by structure box compares two texts by their tokens, names, numbers, strings and signs, in the app's Rust side, and the choice is kept. A line whose tokens did not change is reshaped and not changed: a call spread over lines or a line indented anew reads as layout; a line taken out in one place and put in at another with the same tokens is moved, the lines beside it going with it; a name changed to one other name everywhere it changed is renamed; and every other token taken out or put in is marked where it stands. The bar's second line says what was renamed, in how many places, and how many lines moved and were reshaped.
10. **Review comments.** A press on a right line's number in a file's changes leaves a comment on that line, under its row, as a pull request's review leaves one; Ctrl+Enter or Comment keeps it and Escape drops it. Each comment is kept with the tree by the file's path, the line's number and the line's text, and stands at the line holding that text nearest its number as the file moves on, dashed where no line holds it. Its buttons resolve it, open it again and delete it. The Review pane of the Commit group lists every comment under its file, open ones first with each file's count of them; a press opens the file at the comment's line, and its menu shows the file's changes, resolves, deletes or copies it.
