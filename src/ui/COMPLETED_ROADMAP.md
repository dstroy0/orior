# The orior app: completed roadmap

What the window does that [the roadmap](ROADMAP.md) asked of it, by area. Each time given is measured with real keys on a file of 2,677 lines, from the key's press to the screen showing its answer.

## Responsiveness

1. **Go to File puts the exact name first.** A file whose name is what was typed comes above a longer name that holds it, and a name that starts with it comes next.
2. **No browser autofill.** Every field of the window refuses the web view's list of words typed before, and a search's results stand clear.
3. **Completion as you type.** The list opens on its own as a name is begun, as well as on Ctrl+Space. One question to the language server answers every letter typed while it is out, and the list stands about 0.85 s after the first letter.
4. **The minimap moves with the text.** A scroll or a jump redraws the minimap in the same frame as the code: a page down settles in about 110 ms, minimap and all.
5. **A language server ready before it is asked.** The server for each tab a tree reopens starts as the tree opens, and a file handed to its server is read through at once. A language with no tab open starts no server, and a tree opened in place of another stops the servers the first started. Go to Definition three seconds after a file opens answers in about 135 ms, as quickly as the next one.
6. **A tab back at its saved text shows no change.** Typing a letter and taking it out again leaves the tab marked as saved.
7. **A large file as quick as a small one.** A file of 50 MB and 870,025 lines opens in about 120 ms, goes to its end in about 170 ms, takes a letter there in about 60 ms and pages in about 120 ms: each the time the file of 2,677 lines takes, and each settled as soon. The rest of the file is read in behind the view, by the page's clock 2.6 s from its top or 5.3 s from its end, and a row far down it is drawn as sharply as the first.
8. **Smooth motion counted.** Counted frame by frame on a display that draws 120 frames a second: the lattice draws at about 114 a second and misses none of 60, and a burning fuse holds all 120. A fast scroll through a file of 2,677 lines or of 870,025 holds 60 a second, missing at most 4 frames in 4 s, and reaches 77 to 88 of the display's 120.
9. **Start measured.** Launched cold from the release build, the window is drawn in about 0.96 s and its keys are bound in about 1.04 s: the middle of five launches, each read from the page's own clock against the moment of the launch. The page itself starts about 0.65 s in.
10. **Go to File matched in Rust.** Go to File sends what is typed to files.rs, which holds the tree's files with their names in lower case, reads them again behind the search once they are four seconds old, and gives back the best 200 with the letters that matched, scored as the palette scores them. No list of the tree's files crosses to the page, where reading one took 119 ms on the window's own thread and was done again every 20 seconds. In the release build a keystroke's answer comes back in 1.9 to 3.6 ms over the 2,836 files of this repository, where matching them in the page took 0.7 to 4.8 ms, and the work grows with the tree in Rust and not in the page.
11. **Start under a second.** Launched cold from the release build, the window has its page drawn in about 0.76 s and its keys bound in about 0.79 s, the middle of five launches and the slowest 0.85 s, each read from the page's own clock against the moment of the launch. The lattices start once the keys are bound: their first drawing sets up WebGL, and the menu bar's commands, read before the keys bind, no longer wait behind it.
12. **The highlighter in Rust.** The colors of the editor's lines come from orior's own Rust: each grammar is handed to it once and kept, with a regular-expression engine of orior's own that reads the syntax the grammars write, and the lines an edit reaches, a screen's worth below it, are asked for as the edit is made, the answer coming before the frame that draws it where it can. Until it comes, a line keeps the tokens it had, moved with its line. A jump into a large file colors there off the page's thread. Fifty thousand lines take about 0.12 s against 0.19 s in the page, and every bundled grammar colors as the page did, line for line, over 23,620 lines of the tree and of lines made from each grammar's words. A grammar holding what the engine does not read, lookbehind or a named group, is colored in the page as before, and so is the token at a place that editing asks for at once.
13. **Memory held down.** The memory reading counts each process with the one the app started it from, names a language server by its program and the web view as the web view, and shows on the bar beside the total the name of what holds the most. View, Memory Budget sets the megabytes the app is held to, 2048 where none is set, kept with the settings; a press on the reading lists each part, sets the budget, and stops the servers no open tab needs. While the reading is over the budget it is marked, and the app stops the servers no open tab needs, then the one that holds the most and does not serve the tab shown; each stopped server's tabs lose their diagnostics and are handed to a server again as each shows, and the bar says what was stopped. anchor_sift open with its Python server holds about 300 MB in RAM.
14. **Smooth and gliding scrolls.** A wheel's step over the text or the gutter, and Page Up and Page Down, glide over 130 ms, easing out, a step during a glide taking up from where it is heading; a cursor kept in sight during a glide moves the glide's end and not the view. A touchpad's movement follows the fingers, and once they lift and no event comes for 50 ms, the system giving no run of its own, it runs on from its last speed and slows to rest; any wheel stops it. View, Smooth Scrolling and View, Flick Scrolling set each on or off, kept with the settings, both on where none is kept.
15. **A restart that loses nothing.** orior started again opens each tree with every tab it had, every change not yet saved in its text, each tab's cursor, and the split with its file and its way, which the tree's session now keeps as it changes. The terminal keeps its place: whether its panel is open, the folder its shell stands in, which Git's bash is set to say before each prompt as OSC 7 and any shell that says it is heard, and its last 300 lines, kept a moment after the shell writes and as the window closes. Started again, the panel shows those lines and opens as it was, its shell in that folder.

## The backend

1. **One container, every process under it.** orior's window and its command line each put themselves at the head of a container as they start, and every process either starts, the language servers, kernels, debuggers, shells, database links and runs, and every process those start, stands under it. On Windows the container is a job object, which lists its processes and ends every one of them with orior however orior ends; on Linux and macOS the container reads its descendants from the system's list and ends them as it ends. What orior opens for the reader to keep, a page in the browser, a folder in the file manager or another window of orior's, starts outside it and stays.
   - The memory on the status bar is the container's whole: on Windows each process of the job, one whose parent has ended among them; on Linux each process's private pages; on macOS each process's physical footprint, as the system counts it.
   - A language server that ends is started again the next time it is needed and given back every file it held; one that ends a fourth time within a minute is left stopped, with the last line it wrote to its errors.
2. **One comms layer: keys and channels.** Every part of orior's container speaks and listens through it, each message on a named channel: the server telling the window of its events, and each terminal's shell with every program run in it. A part registers and is given a key, drawn from the system's own source of secrets, that names the channels it may listen and speak on; a part grants the parts it starts only channels of its own, and a message on a channel its key does not name is refused and counted. A process joins at the door, a named pipe that takes no one from another machine on Windows and elsewhere a socket in a folder only the reader can open, and the door takes a key only from the process it was given to or a process under it, by the system's own word for who is at the other end; the key of a part of orior's own process opens nothing there.
   - A run that `orior run start` or `orior run run-file` starts in a terminal of the window's is told to the window as it goes, on a channel of its own under runs: that it started, each line where orior reads them, and how it ended.
   - The Comms window, from the tool strip or View, Comms, lists every part with its process, its grants and what it said and had refused, and every channel with its messages, bytes, refusals and listeners; a channel pressed shows its last 20 messages.
3. **One transfer layer.** A body longer than 64 KiB goes between orior and a process of its container through memory they share, and the message carries only its length and the means to reach it. A region has no name another process could find. On Windows it is a section of the paging file whose handle orior makes in the other process itself, as Chromium's broker does, and the handle given reads the region and cannot write it. On Linux it is a memory file sealed against every change once written, and on macOS a file in the reader's own temporary folder, unlinked as it is made; either goes over the door's socket with the frame that names it, and a region from another process is read only once its seals hold, or on macOS read out whole.
   - A big answer that stalls every channel behind it: a body of any size up to a gigabyte crosses as a region, and the frame that names it is a few bytes; the Comms window counts each channel's bytes that went through the transfer layer.

## Perception

1. **The lattice drawn at the rate it is seen.** A lattice draws a frame only where some point has moved by a whole pixel of the page since the frame before, no faster than one each 33 ms and only in a frame nothing else wants, and draws again at once in a new scheme or theme. Over its loop it draws about one frame in three of those offered, and none while it rests. No one follows its points one by one, and a frame that moves none of them by a pixel shows nothing a reader could see.
2. **No animation below what can be seen.** As a transition starts, its whole change is measured in the display's own units, device pixels for a move or a size and levels of 255 for an opacity or a color. One that changes nothing by a whole unit, or would end within two frames, is not animated: its end is drawn at once. One that changes less than a unit in each of its frames is drawn in whole units, each frame it shows moving something by a pixel or a level, and the frames between show nothing new.
   - Motion the eye cannot pursue, small and unpredictable, needs fewer frames than motion it can pursue, and is given fewer: a twisty's quarter turn of a few pixels is drawn in as many frames as it has pixels to move.
3. **What is in view, and what the motion heads into, in the editor and the grid of rows.** The grid of rows reads the rows in view, as many more the way it scrolls as its speed carries it over two reads, each read timed as it comes, and a few the other way; it holds up to 600 rows and lets go those behind the motion first, the farthest first. The editor draws more rows past the edge it heads for the faster it goes, colors ahead of a view at rest as far as the speed it came to rest with carries it over two screens' coloring, and reads a large file a slice at a time the way it scrolls, and below and above in turn at rest.
   - Motion says where the view goes next: among people watching video all around them, the view 200 ms later lay the way the head was turning in 97% of cases.
4. **What is in view, in the explorer and every list.** A row of the explorer's tree and panes, and of the jobs beside a run, is neither laid out nor painted while it is out of sight, and keeps the height it had: the scroll stands where it would. As a list scrolls, the rows past its edge the way it heads, as many as its speed carries it over two frames' drawing and never fewer than eight, are drawn ahead of it.
   - A tree of thousands of files that lays out every row on each change: only the rows in sight are laid out and painted.
5. **Detail as the motion allows.** While the editor scrolls fast, what the motion hides from the eye waits, more of it the faster the scroll: first the guides, the marks on the word under the cursor and the bracket pair; then the colors of lines not yet worked out, the fold marks, the find matches, the diagnostics and the gutter's marks, all but its numbers, breakpoints and paused line; then every color, the minimap's drawn in one. A frame that runs past its time drops a step whatever the speed. Once the view rests a frame draws everything, and the lines ahead of where it was heading are colored a slice at a time.
   - A change made while the eye moves fast is seldom seen: shifts of up to 1.2 degrees went unnoticed during eye movements of 66 ms or more.
6. **Motion the way the reader moves.** A menu grows out of the point it was opened from, a press's point or the edge of the item a submenu opened from, in a tenth of a second; a tool window comes in from the edge it docks at, the foot, the left or the right; and a pane collapses toward its own edge and comes back from it. None moves while the window is hidden or where the system asks for less motion.
   - The eye places a moving thing a little ahead along its path.
7. **The three limits of a response.** Each call a press or a key makes is watched until it answers. Past a tenth of a second the pointer shows the window at work; past a second the status bar says what the window waits on and for how long; past ten it says how far along the work is where the work tells, as an export of rows does row by row, and offers Stop, which stops the work where it has a stop of its own, a statement, an export, a run of tests or a profile, and the wait always. A hover's and a press's own marks are drawn by the page's styles in the frame the pointer moves.
   - Within 0.1 s a person feels they act on the thing itself; within 1 s their thought goes on unbroken; past 10 s they turn to something else.
   - A delay of the pointer under 50 ms goes unseen: every response to the pointer is held under it.
8. **Waits that read as short.** A bar of progress, where the work tells its size, moves at one pace from one report to the next and never back, and faster toward its end: it draws the share done to the power 1.5, the words beside it saying the share as it is. Each file the editor reads a slice at a time shows one on the status bar, and so does a wait past ten seconds whose work tells its whole.
   - A bar that slows or stops near its end reads as a longer wait than the same time spent steadily.

## Tools

1. **Databases.** The Database window, from the tool strip or View, Database, holds the connections the tree's databases.json names, PostgreSQL, MySQL or MariaDB, and SQLite, each made, changed or taken out from its sheet. orior speaks PostgreSQL's and MySQL's protocols itself, SCRAM, md5 and the clear for one and the native and SHA-2 sign-ins for the other, and reads SQLite through the sqlite3 of the tree's Python, with no driver and nothing fetched. A password goes to the system's keychain only where the reader asks, and never to a file. A connection through ssh goes through the system's ssh, or the one ORIOR_SSH names, with the reader's config, keys and agent, and a tunnel that drops is made again at the next statement.
   - The schema is read a level at a time as each level is opened, a reading can be stopped from the bar, and a statement that makes, changes or drops an object reads again the level that holds it.
   - Run Statement, Ctrl+Enter in an SQL file, runs the statement the cursor stands in or the text selected, and nothing where the cursor stands in no statement; Run SQL File runs each statement in turn and stops at the first that fails. A statement the server finds wrong puts the cursor where the server says, a character past the basic plane before it counted as one.
   - Rows come a page at a time as the grid scrolls, the server holding them and the grid only those in view, and Stop stops a statement as it runs. Export writes the rows held and reads the rest from the same run.
   - A connection that matters opens read-only or asks before each statement that writes, and a write that reaches every row of what it names asks first on every connection, with the count of rows.
   - Each statement commits on its own until the reader begins a transaction, and an open one shows on the status bar, which names the connection of the SQL file shown and the zone its session reads times in, until Commit or Roll Back ends it.
   - Each statement run is kept in its connection's history across restarts, and History runs one again.
2. **Files in an archive.** A zip, and a jar, a wheel or any other zip by another name, a tar, a gzipped tar and a gzipped file open in the explorer as folders, with their files' icons, and their files are read without unpacking them; a path of the tree runs on into an archive past its file, and on into an archive inside it. A file changed in an archive is saved back into it: the archive is written anew beside the old one, every other file's bytes as they were, and put in the old one's place. Deflate, CRC-32, zip, zip64, tar and gzip are orior's own code, with nothing from outside, and Python's zipfile and tarfile read what it writes.
   - Names that come out garbled: each name is read in the encoding the archive's flag gives, UTF-8 or the old DOS page, and the archive's menu, Names' Encoding, reads them in another, Shift_JIS, GBK, Big5, EUC-KR, Cyrillic or Western among them.
   - An archive inside an archive: it opens as a folder too, and a file in it saves back through both.
   - Jars, wheels and tarballs that are archives too: a jar, a wheel, a tar and a gzipped tar open as a zip does.
3. **A Markdown preview.** A Markdown file shown as it reads, beside its text and scrolled with it, or alone in the editor's place, as the reader chooses once for every Markdown file: View, Preview (Ctrl+K V) and Preview Alone.
   - A preview that jumps back to the top as the text is typed, or scrolls out of step with it: each block of the preview is tied to the line it came from, the two scroll by those lines, the one the reader scrolls leading, and the scroll the other makes to follow leads nothing in turn.
   - A preview that differs from GitHub's: headings, lists and task lists, quotes and GitHub's five alerts, tables, footnotes numbered as they are cited, math between dollars and in math fences drawn as MathML from orior's own reading of TeX, and Mermaid's flowcharts, sequence diagrams and pies drawn as SVG by orior's own layout, in GitHub's colors; a diagram of another kind shows as its text, its kind named.
   - Images by a path relative to the file that do not show: an image's path is taken from the file's own folder, and a link to another file of the tree opens it in the editor.
   - A large file whose preview holds up the editor: the text is read again in time the page has free, a block whose HTML is as it was stays as drawn, one whose lines only moved is told its new lines, and only a block that changed is drawn again; a diagram is laid out again only when its own text changes.
4. **Mermaid's other diagrams.** State diagrams, their starts, ends, choices and forks; class diagrams, each class a box of its fields and methods and each relation's kind marked at its ends with its counts; entity-relationship diagrams, each entity a box of its attributes and each relation's counts at its ends; mind maps, each idea hung from the one it is indented under; Gantt charts, tasks as bars over a scale of days by section, those done, active, critical and milestones each marked; journeys, each task with its score and its actors; and git graphs, commits along their branches' lanes with merges and tags, all drawn by orior's own code as GitHub draws them.
   - A diagram shown as code in the preview and as a drawing on GitHub: `classDiagram`, `stateDiagram`, `erDiagram`, `gantt`, `journey`, `gitGraph` and `mindmap` are drawn beside flowcharts, sequence diagrams and pies.
5. **A live preview pane.** The preview shows, beside the text or alone, each kind of file that sets how something looks and runs nothing, drawn as it is typed with the place the cursor stands marked in it: Markdown; a page of HTML in a frame that runs none of its scripts, with the stylesheets it links; a CSS file over a page made from its own selectors, the elements of each selector holding its text; SVG; a Mermaid file as its diagram; and LaTeX as its pages, made by the TeX the toolchains give and drawn by pdftocairo. View, Preview (Ctrl+K V) and Preview Alone.
   - A page reloaded whole on each change, its scroll, its form's fields and its state lost: a change is patched into the page where it changed, each node of the same kind in the same place kept, and while a stylesheet the page links is edited in its own tab, the page stays shown, the sheet swapped into it as it is typed, at the same scroll.
   - LaTeX that takes seconds to show a change: the text in the editor is made, saved or not, one make at a time, the last pages staying until the next are drawn and the errors of a make that failed listed over them, each taking the editor to its line; SyncTeX's boxes, read by orior's own code, mark on the pages the line the cursor stands on, and a press on a page takes the editor to the line set there.
   - A diagram drawn again on every key: a diagram is drawn again only when its own block changes, and a move of the cursor draws nothing again.
6. **Requests.** A file of HTTP requests, `.http` or `.rest`, written as JetBrains' HTTP Client writes them and colored as it is written: Ctrl+Enter, or Send over the answers, sends the request the cursor stands in, and its answer shows beside it in the preview, its status, how long each part took, its headers, what was sent, and its body, JSON laid out and an image as itself. Variables come from the file and from the environment chosen, read from http-client.env.json and the reader's http-client.private.env.json. Run, Send Request, Copy as curl and Private Environment File.
   - A sign-in and a cloud account to send a request: none; requests are `.http` files in the tree, plain text kept with git.
   - Secrets in a file that gets committed: each environment's private values come from the reader's http-client.private.env.json, which Private Environment File makes beside the file and names in the tree's .gitignore as it makes it.
   - Answers lost once the next is sent: each request keeps its last ten answers, the last first, and two of them checked are compared side by side.
   - Requests copied from a browser or a terminal: a curl line pasted into the file becomes a request, one copied for cmd as well, and Copy as curl gives the request back as a curl line.
   - A client that holds a gigabyte to send text: requests go out from the window's own process over orior's own HTTP/1.1, and HTTPS through the system's own TLS, Schannel, Secure Transport or libssl, the certificate checked against the system's roots and the host's name.

## How developers work

1. **Menus that stay where they are, and their keys in sight.** No menu orders itself by use: an item stands where it was learned, and only a search ranks what it finds. Holding Ctrl or Alt alone for half a second shows, over each button in sight that has keys, the keys that press it, from the keys it names or the keys its title ends with, and over each menu's title its Alt letter; letting go, another key, a press, a wheel or the window going to the back takes them away.
   - How fast an item is chosen depends on its place staying the same.
   - Many people never learn an item's keys unless the keys are shown where they already look.
2. **Code seen without going to it.** Peek Definition (Alt+F12, Ctrl+Shift+I), Peek Usages (Ctrl+Alt+F7) and Peek Callers show the places the language server finds over the editor under the cursor's line, in an editor of their own: a file a tab holds shows its live text, changes not saved and all, and takes edits as the tab does, and one no tab holds shows as it was read. No tab opens, several places stand in a list the arrows go through, and Escape closes the peek. Enter, or Open, opens the place in a tab that is a preview, its name in italics, until it is edited or its tab pressed twice; the next preview opened takes its place.
   - Developers spent 35% of their time on the mechanics of moving between code, and a fifth of it reading code in one fixed view.
3. **What a file is for, before it is opened.** The pointer resting on a file in the explorer for half a second shows a card beside it: what the file's first comment says, read past a first line of `#!` and past a comment of copyright or license, a Python module's docstring and a Markdown file's first paragraph counting as one, and then the files of the tree that use it, each opening at a press. A file uses another where it names the other's file name, as an import, an include, a link or a stylesheet does, or where a line that imports, uses, includes or inputs names it without its extension; the tree's files are read on every core the machine has. The card goes when the pointer leaves the file and the card, at a key, and when the explorer scrolls.
   - Without cues before opening, developers open file after file to judge each one.
4. **The task's code in one place.** Gather Lines (Ctrl+Alt+G) adds to the task the lines selected, or, with none selected, the declaration the cursor stands in down to the next at its depth; Gathered Lines (Ctrl+Alt+Shift+G) shows the task's pieces side by side over the editor, each in an editor of its own of its file's text, and a piece's name opens its file at its lines. A file a tab holds shows as the tab has it, changes not saved and all, and takes edits as the tab does. Each piece keeps the text of its first line and is found again by it where lines come or go above it. Tasks are named, one is the task gathered into, and each keeps its pieces with the tree from one run to the next.
   - Developers kept what they found in memory, in notes, or in tabs that closed, and went back to find it again.
5. **Notices at the reader's breaks.** A notice that answers what the reader did, within a second and a half of a press or of a key that gives a command, shows at once; any other needs nothing done and waits for a break in the work: a save, a commit, a run's end, or the keys at rest for two seconds, the last of those held on the bar and each of them in the bell. No notice takes the keys. View, Focus holds every notice until it ends, the bar saying how many it holds, and a press there ends it.
   - Suggestions offered at such a break were taken up 52% of the time; those offered in the middle of a task were mostly dismissed.
   - An interruption on the screen that demands attention slows the reading of code.
6. **A change reviewed by its structure.** Git, Review Changes by Structure shows the tree's change against its last commit, or a commit's against its first parent, as the declarations it touches across its files and not file by file: each piece its declaration's lines, those taken out and those put in marked, and one added or taken out whole said to be. The pieces that call one another stand together in a row, each caller before what it calls, and the names a piece calls go to those pieces; a piece's name opens its file at its line. A commit is named with who made it; authors stay off everywhere else until the reader turns them on.
   - In about 40% of pull requests more than half the changed functions call each other, and the function a caller needs is often in another file.
   - A function moved shows as one move, not as lines taken out of one file and lines put into another: one taken out of a place and put in at another, in the same file or another, by its name and kind and with most of its lines kept, is one piece, named with where it stood.
7. **The debugger as simple as print.** Run, Print Here (Ctrl+Alt+P) puts on the cursor's line a message breakpoint that writes the line's values each time it runs under the debugger, the file itself unchanged: the expression selected, or each name the line reads with its value. The print statements a change added, in each language's own form, from Python's print( and JavaScript's console.log( to Rust's dbg! and C's printf, stand in the Commit window, each opening at its line, and Take Them Out takes every one of them out in one step: from a tab that holds its file as one edit undo takes back, and from a file no tab holds as it is written.
   - Most developers never start a debugger, use only its plainest parts, and print values instead.
   - Print statements left in by mistake are a common part of commits.

## Plugins

1. **Plugins that draw.** A plugin of kind `script` runs code of its own and draws through orior's calls, `orior` in its worker: it lays marks on a file's lines, each a dot in the gutter in the color of its kind with a word after the line's end; lays an overlay of text under a line; shows panels of its own down the window's right side, each its HTML in a frame that runs none of its scripts; sets the label of a file's tab; reads the theme's colors; and changes the window's chrome, a badge on the top bar and the color of its signal. It hears when a file opens, changes and saves and when the cursor moves, and reads and writes the tree's files.
   - Plugins that reach into the editor's own parts and break when it changes: a plugin draws through the calls alone, and names the form of the calls it was written for, `api` in its plugin.json; orior keeps each form it has given, and a plugin of an older form gets that form's calls, each answered as it was.
2. **Plugins off the editor's thread.** Each script plugin runs in a worker of its own, apart from the editor and from every other plugin, and one that is slow or stuck holds up neither the keys nor the others.
   - One plugin's slowness that freezes all the others: each plugin has a worker of its own; each is asked every second whether it is there, and one that has not answered for two seconds is named on the status bar with how long, and Stop there ends it.
   - A window slowed by a plugin the reader cannot name: View, Find the Slow Plugin turns half of the plugins on off at a time, asking each time whether the window is still slow, until one is left, names it, and sets each plugin back as it was.
3. **Plugins that write files with care.** A plugin's write the system refuses is not left to fail: the reader is asked, the plugin named, whether to write the file with the rights it needs; on Write with Rights the system asks for the rights in its own way and the file is written, and on Leave It the file stays as it was and the plugin is told the system refused.

## Settings

1. **Saving where rights are needed.** A file the reader may not write is saved after the system asks for the rights: a save the system refuses asks the reader first, and on Write with Rights the text is staged in a file of orior's own and copied over the file with the rights.
   - A save with raised rights that fails, or offers no way to raise them: on Windows the system's own prompt raises orior's own program, run again as `orior write-raised`, which writes that one file and ends; on Linux pkexec runs cp; on macOS the system's authorization does; a reader who declines leaves the file as it was.
2. **Keys.** Preferences, Keys sets any command's keys by pressing them, two at most for a command, each a press, two presses, a button of the mouse past its first three, or the wheel turned with a key held; each is taken off by its cross, and Reset gives a command back the keys of the set. Keys from chooses orior's own keys or JetBrains', and the mouse's back and forward buttons go back and forward as Alt+Left and Alt+Right do. A command's keys show where the reader reaches it, in the menus, the palette and the toolbar, and change there as they change in Preferences.
   - Keys that do the wrong thing on AZERTY, QWERTZ and the like, as Undo closing a tab: a letter or a digit is bound by the character it types or by its place on the board, as the reader sets, and on a layout that types none of the Latin alphabet, as a Greek or a Cyrillic one does, by its place.
   - Two commands on one key, found only when one of them fails: Preferences lists each key that more than one command holds, with those commands, and each set of keys holds no key twice but where the commands act in different places.

## Version control

1. **Branches.** A Git menu holds Commit, Push, Pull, Branches and New Branch. Branches, or a press on the branch in the top bar, lists every local branch and then every remote one, newest commit first, the one open checked. Each opens a list of its own: Switch, a remote branch made a local one that follows it; Merge into the branch open; Rebase the branch open onto it; and for a local branch Rename and Delete, a branch with commits no other holds deleted only after a yes. New Branch makes a branch from the one open and goes on it. What git says shows on the status bar, its own words where it refuses, and the tree's changes are read again after.
2. **Conflicts.** A file a merge left in conflict opens from Git, Resolve Conflicts, or from its row in the Commit window, in a window of three panes over the editor: the branch open's text on the left, the result in the middle, and the text the merge brought in on the right, each stretch the three share level across them and each side named as git named it. Each conflict takes its lines in the middle from Yours, from Theirs, from Both one after the other, or as written by hand in Edit, its open result striped until then. Once none is left open, Mark Resolved writes the result, stages the file as resolved, and gives an open tab of it the result. F7 and Shift+F7 step from conflict to conflict.
3. **Part of a file in a commit.** A changed or new file's arrow in the Commit window opens its changes under it, each change with a box of its own and each line taken out or added with one, the file's own box half filled while it is taken in part. The commit takes of the file only the lines whose boxes are checked, made from an index of its own so that nothing else staged goes with it, and the lines left out stay changes of the file for a later commit. A file that changed since its changes were opened is refused until they are opened again.
4. **Compare.** A revision in the Timeline opens beside the file as it stands, or beside another revision from its own list, the older on the left. Select for Compare on one file in the explorer and Compare with it on another puts the two side by side, and Compare with Clipboard in the Edit menu puts the clipboard beside the open file. A box over the changes sets changes to white space aside, which then show as the same, and the choice is kept.
5. **The commit graph.** The Git pane draws every branch's commits as a graph, the newest first, each in its column with a line to its parents, a merge's dot hollow, and the branches and tags at it, its subject and its date. A press on a commit, or Right, opens the files it changed under it, and a press on one of those sets the file as the commit left it beside the file as the commit before it did, the bar naming who made the commit. The field over the graph searches the whole history by subject, id or branch. Git, Authors puts each commit's author beside it and in the search, and is off until the reader turns it on. The graph is laid out in the app's Rust side, two thousand commits at most.
6. **Line history.** Git, Line History puts a column in the gutter beside the line numbers with the date of the commit that last changed each line, and its author where Git, Authors is on, on the first line of each run of lines one commit left, the commit's id and subject under the pointer. It reads the text as the editor holds it: a line typed in and not yet committed has no mark, the lines after it keep theirs, and the column is read again as the text or the file's last commit changes. A press on a line's mark sets the file as that commit left it beside the file as the commit before it did.
7. **Stash and cherry-pick.** Git, Stash Changes puts every change aside, new files with them, under a message, and Git, Stashes lists each stash, the newest first, to apply and keep, pop, or drop. Git, Cherry-Pick lists the commits of other branches the branch open does not hold, merges aside, and applies the one chosen as a commit of its own; a commit already applied under another id is left out, known by its author, the time its author made it and its message. A commit's menu in the Git pane cherry-picks it too. Where a change does not fit, its files stay in conflict for Resolve Conflicts, and a commit after finishes it.
8. **More than one repository in a tree.** A tree's repositories are found under it, the one it is in and each folder up to four deep that holds one of its own. The Commit window lists each one's changed files under a row that names it, its branch and how many files differ; a commit goes to each repository that holds a file taken, and Commit and Push pushes each. The branch on the status bar is the repository open's, the one that holds the file shown, named with it, and the Git menu's branches, stashes, cherry-pick, pull and push act on that repository. The Git pane chooses whose graph it shows. A file's last commit, Timeline, Line History and roll back are read from the repository that holds the file.
9. **Compare by structure.** The changes view's Compare by structure box compares two texts by their tokens, names, numbers, strings and signs, in the app's Rust side, and the choice is kept. A line whose tokens did not change is reshaped and not changed: a call spread over lines or a line indented anew reads as layout; a line taken out in one place and put in at another with the same tokens is moved, the lines beside it going with it; a name changed to one other name everywhere it changed is renamed; and every other token taken out or put in is marked where it stands. The bar's second line says what was renamed, in how many places, and how many lines moved and were reshaped.
10. **Review comments.** A press on a right line's number in a file's changes leaves a comment on that line, under its row, as a pull request's review leaves one; Ctrl+Enter or Comment keeps it and Escape drops it. Each comment is kept with the tree by the file's path, the line's number and the line's text, and stands at the line holding that text nearest its number as the file moves on, dashed where no line holds it. Its buttons resolve it, open it again and delete it. The Review pane of the Commit group lists every comment under its file, open ones first with each file's count of them; a press opens the file at the comment's line, and its menu shows the file's changes, resolves, deletes or copies it.

## Testing

1. **A test runner.** The Tests window, on the tool strip, and Run, Run All Tests run the tree's Python tests with pytest, or with unittest where the tree's Python has no pytest, and list them in a tree of their own, by file and by test, each marked passed, failed, skipped or running as its run says, a failure's message under it and each test's time beside it. A failed test opens at the line it failed on, any other where it is written, and Run Failed runs again the tests that failed, in one press. Run, Find Tests and `orior run tests` list them as found.
2. **Tests from the gutter.** A mark beside each test in the editor, colored by its last result, opens its menu: run it, run it with coverage, or debug it, pytest running it under debugpy with the breakpoints set.
3. **Coverage.** A run with coverage, by Run, Run All Tests with Coverage or a test's own menu, runs pytest under orior's shim, which marks each line of the tree's files that runs by `sys.monitoring`, or by `sys.settrace` where Python has no `sys.monitoring`. The gutter marks each line that ran and each that could run and did not, and the Tests window lists each file's share of its lines that ran, under the run's whole share.
4. **Tests in parallel.** A run spreads its files over the machine's cores, a process of pytest to each share, the files of most tests first, each to the share that holds the fewest; each test's result comes in as its process prints it, and each failure's details as its process ends. Run, Run Tests in Parallel, or the window's Parallel, keeps a run to one process where it is off.

## Debugging

1. **Breakpoints with conditions.** A press with the other button on the gutter's breakpoint strip opens the breakpoint's menu: Add or Edit Breakpoint, Add Message Breakpoint and Remove Breakpoint. Its sheet sets the expression it stops only where it holds, the count of hits it stops at, and the message it writes to the console in place of stopping, `{name}` in the message writing the value of `name`. The gutter draws a breakpoint that holds a condition or a count with a bar across it, and one that writes a message as a diamond.
2. **Stop on exceptions.** The debug bar's Exceptions lists the exceptions the session's debugger can stop on, by its own names, Python's raised and uncaught among them, each set on or off as the session runs and kept for its language; a Python session stops where nothing catches an exception until it is set otherwise. A stop on an exception says what was thrown and its message, writes its stack to the console, and Continue carries on past it.
3. **Values under the pointer.** While a program is stopped, the pointer resting on a name in the editor shows its value in the frame chosen, as a tree that opens a level at a time where the value holds more.
4. **Breakpoints and watches kept.** Run, Export Breakpoints writes the tree's breakpoints, with their conditions, counts and messages, and the watches to a file chosen, and Run, Import Breakpoints takes them in beside the tree's own. A variable's menu keeps its value as it stands, three levels deep, and Compare with Kept sets a value kept beside the same value read now, field by field, each field that differs marked and counted.
5. **Attach.** Run, Attach to Process lists the machine's processes, read from the system's own list in milliseconds, each by its name and the line it was started with, and debugs the one chosen in its language. Run, Attach to Address reaches a Python program that debugpy runs listening at a host and a port, as one in a container with its port published, the folder its files are at there taken as the tree. A program attached to runs on when its session ends, and can be attached to again.
6. **Two programs at once.** More than one session runs at once, each with its own threads, frames and variables; the debug bar's chooser picks the session the steps act on, and a stop in any session chooses it. A process a Python program starts is debugged with it, with the breakpoints set, and stopping a session stops the sessions it started.
7. **Stepping of the tree's own.** Run, Stepping sets for each tree whether a step keeps to the tree's own code, the modules, paths and functions a step passes over, by debugpy's rules for Python and lldb's patterns for C and Rust, and the patterns of the frames a stop hides, a note under the frames counting those hidden.
8. **Memory and machine code.** A variable's menu shows the memory it stands in, sixteen bytes a row as hex and as text, paged on and back, and Run, Show Memory reads it at any address. A frame's menu shows a Python frame's bytecode, by `dis`, or a native frame's instructions about where it stopped, the line's own marked. Stop When It Changes, on a variable's menu, and Run, Stop When Memory Changes stop the program where the bytes change. On Windows, where lldb-dap ends at a watchpoint's stop, the watchpoint is lldb's own and a script of orior's stops the program at the next instruction it runs.
9. **Across languages.** Run, Debug File with Its C starts the Python file under debugpy, stopped before its first line, attaches lldb to the same process as a session of its own beside it, and lets the program run; breakpoints in the tree's C, C++ and Cython files stop it in the native session. Step Into on a Python line that calls the tree's own native code stops at the first line of it that runs, by a breakpoint of one stop on each line of the tree's files in the modules the process loaded, a Cython file's lines among them by the `#line` its C names them with; Step Out of the C the Python called comes back to the Python at the next line it runs.
10. **Back in time.** Run, Record and Debug File runs the Python file under orior's recorder, which keeps each line of the tree's own code the run runs with the values its frame's names held, by `sys.monitoring`, or `sys.settrace` where Python has none. Once the run ends, an adapter in orior itself steps through the recording: Continue, Step Over, Into and Out go forward, Step Back and Run Backward go back, to the frame's line before or the last breakpoint, and a variable's menu lists the values the name took through the run, each with the line that gave it, a press on one going to that line as it ran.

## Layout

1. **Groups of tabs.** Each side of a split holds tabs of its own, any file in either side or both, a file in both showing the same text with the selections, folds and place each its own. A file opened, from the tree, Go to File or anywhere else, opens on the side last pressed in, and Save, Format, Run File, Close and Debug act on that side's file. View, Move to Next Split, Ctrl+Alt+Right, carries the file shown to the other side, making a split where there is none, and Open in Next Split, from the menus, a tab's menu or the tree's, opens a file there. Unsplit takes the split's files back to the first side, closing the split's last tab closes it, and the split comes back with its tabs as the tree opens again.
2. **Tool windows anywhere.** Debug and Terminal dock at the left, the right or the foot of the work, and the explorer, the definitions and the jobs at the left, the right or the foot of their view, by dragging the window's icon on the strip onto the side its place lights, or from the icon's menu or View, Tool Windows. A sash on each window's inner edge drags its width, or at the foot its height, and each side's size is kept for each window. View, Open Tool Window in a Window opens the terminal, the explorer or the jobs alone in a window of its own, the terminal with a shell of its own, and a file opened from the explorer there opens in the window it came from. An icon's menu takes it off the strip, its window closed, until Tool Windows brings it back.
3. **More than one window.** Each window is a program of its own on one tree, with its own tabs, terminals, servers and debugger: File, New Window opens another on the same tree, and Open Folder in New Window one on another. A tab dragged out of the window, or its menu's Open in New Window, opens its file in a new window with its changes not saved, and leaves this one. View, Move Window to Next Display moves the window to the next of the machine's displays, maximized there where it was here.
4. **Terminals side by side.** The terminal panel holds a shell in each tab of its strip, each named by the folder it stands in. Terminal, New Terminal, Ctrl+Shift+`, opens another, Split Terminal, Ctrl+Shift+5, shows two side by side, and the keys go to the one last pressed in, marked at its top. A tab's × ends its shell and closes it. Each shell's folder and last lines, the tab shown and the one beside it come back with the window. Text typed into a shell as it starts, or a line run in it, waits until the shell's prompt is up.
5. **Tabs down the side.** View, Tabs Down the Side sets the first side's tabs in a column beside the editor in place of a row above it, with a split beside or under the editor as before. A tab's menu puts it in a group named by the reader, and each group stands under a header with its count that folds it, its menu renaming it, letting its tabs go or closing them; the groups come back with the tree. Go, Marked Files, Mark File, Ctrl+Shift+0, marks the file shown, nine at most, each opened by Ctrl and its number; its number shows on its tab, the column lists the marked files first, and Marked Files opens, moves or lets go of each.
6. **A status bar of the reader's.** Each item of the status bar, and each part of the editor's line on it, is shown or hidden from the bar's menu or View, Status Bar, moved by the menu's Move Left and Move Right or by dragging it along the bar, and kept; Reset the Status Bar puts it back. View, Hide Tool Strip Until Its Edge hides the tool strip, the work taking its room, until the pointer reaches the window's left edge, where the strip slides out over the work and back a moment after the pointer leaves it.
7. **Menus and a toolbar of the reader's.** File, Menus and Toolbar opens menus.json in orior's own folder, made with a note on its parts where it is not there, and the window reads it again each time it comes back to the front. Each item names a command, under the reader's label where it gives one, or a line, or a list under a label of its own; an item naming no command is drawn and cannot be chosen. A menu named as one of orior's stands in its place, the others stand before Help, and hide takes orior's away by name, every command keeping its keys. The toolbar's items lay out a row of buttons under the menus, each with the icon it names or its label's first letter, shown or hidden by View, Toolbar. A menus.json that is no JSON is said on the status bar, and orior's menus stand.
8. **More than one tree in a window.** File, Add Folder to Window and Add File to Window mount a folder or a single file from another place beside the tree, under its own name, each with its own place in the explorer after the tree's own; a file opened from outside the tree is mounted on its own. Its files open, save, and reach the language servers, the debugger and runs as the tree's do, the mounts come back with the tree, and a mount's menu takes it out of the window with its tabs. File, Open, Workspace opens a .code-workspace file as such a window: the first of its folders as the tree, and the rest mounted beside it.
9. **Focus that follows the pointer.** View, Focus Follows the Pointer, kept, gives the keys to the editor, to the shell of the terminal under the pointer, or to the row under the pointer of the explorer's, the jobs' or the debugger's lists, once the pointer has rested on it a moment. The keys stay where they are while a menu, a sheet or Go to File is open, while a field is being typed in, and while a button of the pointer is held.
10. **The system's title bar.** View, System Title Bar draws the window with the system's own title bar and controls, the bar's own controls standing down and the system's bar moving the window; the choice is kept in settings.json, and the window reads it as it opens, before it shows.

## Running and measuring

1. **A profiler.** Run, Profile File runs the Python file shown under a profiler and opens the Profile panel, where a flame graph of the run's time by function grows as it goes, and Memory shows the process's own memory as it grew, by the functions running then; the program runs at its own speed under it. A bar's width is its share, the pointer resting on it says its function, where it is written, its share and its time or memory, a press opens the function there, and its menu zooms the graph to it, out again, or back to the whole run. Output holds the program's own lines. Profile File on Another Machine… runs it on a machine reached by ssh, named as user@host:folder, by the same path there, and Stop Profiling ends a run.
2. **Runs on another machine.** File, Open, Folder on Another Machine… opens a window on a tree at an address: user@host:folder over ssh, its keys and agent its way in; docker:container:folder in a running container; or wsl:distribution:folder in WSL. File, Open in Dev Container brings up the tree's own container as its .devcontainer/devcontainer.json describes it, from its image, its Dockerfile or its Compose service, with its environment, mounts, run arguments and commands, finds it again the next time, and opens the tree in it. orior sends the machine its own server, built with Rust's target for a Linux machine, and the editor, the explorer, the terminal's shells, the jobs and the debugger work there; a file saved in a container is the tree's own file through the mount. The status bar names the machine and how the link to it stands. A link that drops is made again, each open tab handed to its server there again, and a run that was going when it dropped goes on there and is read again from its first line.
3. **Containers.** View, Containers opens a window of the machine's containers. Docker lists each container under its Compose project and service with its state, and Kubernetes each pod of the cluster kubectl names under its namespace with how many of its containers are ready; each list is read again every few seconds while the window shows, and a list that cannot be read says why. A press on a row reads its last 500 lines of logs beside the list, and a pod's menu reads each of its containers'. A container's menu starts, stops or restarts it, runs a command in it with the output beside the list, opens a terminal in it, or opens a folder of it in a window of its own, where the editor, the jobs and the debugger work in it; a pod's menu opens a terminal in it.
4. **Executables.** Any folder opens as a tree, and each program its build scripts make is a job of the executable group, built by the build's own tool with its lines as the job's output: Cargo's binaries, the executables of a CMake or a Meson project, Go's main packages, .NET's programs, the executables of a build.zig, the program a PyInstaller spec freezes, and a package.json's bin, built by Node's own single executable, Bun or Deno; orior adds the blob to a copy of Node itself where Node is older than 25.5. A build's end names the file it made, to run in the terminal, to build and run again in the job as orior runs it or as the system runs a program opened on its own, to copy beside it the libraries it loads through a PATH, or to copy its path. The end says each library the program loads from outside its own folder and the system's, one found nowhere, Visual Studio's debug runtime and the Visual C++ Redistributable, a Linux program's run paths of the machine that built it and the newest glibc it asks for, a .NET program's runtime that a program opened on its own does not find, and each module a frozen Python program lacks, with what sets it right; a run says its time to its first line, and a Windows code that means a DLL did not load. Go and Rust build for another system and processor, with zig cc for their C and rust-lld for Rust's musl targets; .NET publishes one self-contained file; Meson sets up Visual Studio's environment itself; a program is signed with the certificate settings.json names; the tree's own tools come first on the PATH; a run takes the folder chosen and the tree's .env; and each build of a commit is compared with the last build of it, byte for byte, the commit's time set as SOURCE_DATE_EPOCH and the tree's folder mapped out of release builds.
5. **Deployments.** A build's files go to the places a tree names in deploy.json, to several at once, each deployment a job of Build that previews, sends or rolls back. A place is a machine orior reaches, over ssh with the keys the system's agent holds, in a container or in WSL, or a folder on this machine. The preview lists every file that goes and where, each file left out with the pattern that leaves it out, a file changed at a place since it was last sent there with its differences, to keep or to replace, and each file a place holds that the tree no longer does, to keep or to delete. The files go as a tar stream, which keeps each file's bytes, line ends and all, and the mode git's index gives it. A machine takes each deployment as a new release beside the one it runs, the files it keeps carried into it, and every machine is turned to the new release only once all of them hold it: a place that fails leaves each on the release it had. Each machine keeps its last releases, and Roll Back turns every one to the release before. orior keeps no key and no password, and a machine that asks for a password is told how a key reaches it.

## Notebooks

1. **Notebooks.** A Jupyter notebook opens as cells, and so does a script of `# %%` cells; each opens as its text again from its tab's menu. A code cell runs on its own on the notebook's kernel, Shift+Enter going on to the next, and its output shows under it: printed lines, values, images, Markdown, and HTML in a frame of its own with no reach into the window; an output of more than 200 lines shows its first and last 40, the whole a press away. A Markdown cell shows as it reads. The kernels are those whose specs Jupyter keeps and each Python orior finds, the tree's environment first, and a Python without ipykernel is listed with the line that installs it, run in the terminal with a press. Each cell shows when it ran in the kernel's order, and a cell whose output stands on a cell changed, run again or deleted since is marked out of date, naming those cells. Run All, Restart and Run All, Interrupt, Restart and Stop are each one press, and Stop ends the kernel's process where the kernel does not answer; Check from the Top runs every code cell from the first in a kernel of its own and says the first that fails. A line `name = value  #@param` draws a field, a list or a slider, as Colab writes it, and a map beside the cells shows each as a block colored by its kind and its state. Debug, from a Python cell's menu, stops the cell at the breakpoints set in its gutter, or at its first line where it has none, its variables in the Debug window, and the debugger lets go of the kernel once the cell has run. A notebook saves as Jupyter writes it. Its diff shows its cells' sources and outputs, its run counts, ids and metadata aside; a commit can leave its outputs and run counts out while its file keeps them; and a merge in conflict is resolved cell by cell, each cell one side changed taken from it, and each cell both sides changed shown from both to take one.
